# 重定义技能分类体系

> 计划位置：第 2 个（共 4 个）；前置：20261112-唐启云-沉淀技能提炼规则；后继：20261111-唐启云-统一文档站导航技能命名（阻塞）、20261112-唐启云-收敛技能元数据字段

## 背景

本集定位是「个人综合实践技能集」：以个人实践与习惯沉淀为主，当前内容集中在研发领域只是因为当前工作重心在此，后续还要沉淀写作、研究、设计、数据、办公、生活等领域的技能。

现行分类表有四处结构性缺陷：

1. **维度混杂**：`dev` / `design` / `ops` 是职能，`writing` / `research` 是活动，`data` / `office` 是对象或介质，`meta` 是层级，`imported` 是来源——同一层混了五种切分依据，归属只能凭感觉。
2. **`imported` 不是分类**：来源已由 `metadata.source` 承载，放进分类会让「导入的研发技能」无处可归。
3. **九成空转**：9 个分类只有 2 个在用，7 个长期预留；小分类 5 个只有 `profile` 在用。
4. **分类被写进技能名**：命名规则 C-3 让分类 id 成为安装引用的组成部分，分类一旦演进就要连带改名。

上一版评估曾提出以「交付物形态」为一级（code / content / insight / visual / ops / collab），该方案的问题是以研发样本归纳维度，非研发领域的技能没有自然归处（如个人事务、学习方法），不符合本集的长期定位。本任务改用「实践领域」为一级，交付物降为辅助判据与标签。

## 目标设计

### 一级：实践领域（单选，进技能名）

判据：这个技能主要在什么领域解决任务。领域按实践对象划分，不按职能、不按介质。

| id | 名称 | 覆盖范围 | 示例 |
| --- | --- | --- | --- |
| `code` | 编码 | 软件实现、构建、工程化、界面实现 | 前端规范、构建质量、接口契约、设计还原 |
| `writing` | 写作 | 书面表达与知识条目 | 文档站导航、周报、邮件、长文、笔记 |
| `research` | 研究 | 检索、分析、评估、对比 | 调研、选型、竞品对比、资料核实 |
| `design` | 设计 | 视觉、交互、版式、配色 | 视觉规范、版式规则、设计评审 |
| `data` | 数据 | 数据处理、统计口径、可视化 | 清洗规则、指标定义、图表选择 |
| `office` | 办公 | 文档表格演示的事务性使用 | 演示制作、表格建模、日程与事务 |
| `ops` | 运维 | 部署、发布、稳定性、自动化 | 发布流程、监控排查、脚本化 |
| `life` | 生活 | 个人事务与日常安排 | 旅行规划、健康记录、财务整理 |
| `meta` | 元技能 | 技能与规则本身、协作机制 | 技能创建、任务归档、会话沉淀 |

空领域不建目录、不进导航，仅在 `categories.json` 登记 id 与定义，防止未来重名。

### 二级：技能形态（单选，进技能名）

| id | 形态 | 判据 |
| --- | --- | --- |
| `profile` | 规范 | 约束「怎么做」，以条文、检查清单、反例承载 |
| `practice` | 流程 | 规定「按什么步骤做」，以工作流与分支判定承载 |
| `template` | 模板 | 可直接套用的文件骨架或配置集 |

`guide` 并入 `profile`；`preset` 并入 `template`；`bundle` 取消——它是分发产物且与「一技能一主题」冲突。

### 不进分类的维度

交付物形态（代码 / 文档 / 报告 / 视觉 / 数据 / 演示 / 动作）、技术栈与端、来源、成熟度、依赖，全部走字段与 `triggers`。若后续检索需求明显，再引入可选 `tags` 字段，本次不引入。

### 命名规则修订

- 命名仍为 `fxri-<领域>-<形态>-<主题>`。
- 禁用词表改为「不得与领域段或形态段语义重复」＋少量空泛词（`tool` / `skill` / `general` / `all`）；`web` / `vue` 这类技术栈名放行，可作主题。

# 沉淀技能提炼规则

> 计划位置：第 1 个（共 4 个）；前置：无；后继：20261112-唐启云-重定义技能分类体系

## 背景

把外部仓的规范提炼成技能这一轮里，返工三次的原因都不是条文写得不好，而是三条流程规则没写进载体：擅自扩大取材范围、把具体组件写成硬要求、依赖缺失时才在加载后发现。规则不落在载体里，下次提炼仍会凭记忆执行。

本任务只沉淀这三条流程规范，与分类体系迁移无耦合，可先行交付。

## 实施方案

1. `.tasks/conventions/common.md` 新增三条：

   **C-5 取材边界**

   - 要求：把外部仓或历史条文提炼进技能时，取材范围只取用户明确点选的条目（用户给定整文件或整批范围时以该范围为准）；同一索引文件里未点选的行、同族仓的同类条文，不得以「同族」「配套」为由自行纳入；确需纳入先说明理由并取得确认。索引只给标题时须回详情文件读该条正文，不得凭标题臆测内容。
   - 反例：把未点选的条目连同「属同一族」的理由一并纳入提炼方案，用户无法区分哪些是自己选的。
   - 理由：提炼是范围敏感动作，自行扩大后复核成本全部转移到用户侧；同族不等于同类，跨文件同义条文仍需用户裁定。

   **C-6 分层与按需取用**

   - 要求：技能正文分两层——无条件原则（任何工程成立）与条件原则（前提成立才生效）；依赖具体组件、包、工具、平台的做法只进 `references` 适配表，正文用「能力位」描述、不点具体名称。每条规则写明适用前提与「项目无对应物」的处置，缺省处置是跳过，不得要求为满足规则新建包装组件、占位资源或替代实现。技能 `description` 末尾声明依赖缺失时相关条目自动跳过。
   - 反例：正文写死「必须使用某组件」，使没有该组件的项目被迫新建替代物。
   - 理由：技能跨项目分发，项目环境不可预知；把依赖写成硬要求，会把「不适用」判成「违规」。

   **C-7 描述与触发**

   - 要求：`description` 写全「做什么 + 何时用 + 不涉及什么」三段，并在末尾声明依赖缺失时相关条目跳过；`triggers` 覆盖意图与近义表达，不用单个专有名词凑数；排除项写进描述，不依赖用户猜。
   - 反例：描述只堆主题词，触发后才发现技能管不了当前场景。
   - 理由：`description` 是唯一常驻上下文的部位，匹配精度直接决定按需加载是否成立。

2. `.tasks/conventions/index.md` 新增 C-5 / C-6 / C-7 三行，归属 `common`，单一事实源 `common.md`。

3. 同文件「三、用法说明」补一句：规范载体是提炼技能时的唯一判据来源；技能正文与载体冲突时以载体为准，并同批修正技能。

4. `.changeset/` 新增 patch 变更集，条目逐条 `- 类型：描述`。
