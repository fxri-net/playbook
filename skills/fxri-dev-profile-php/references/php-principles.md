# PHP 原则详解

## 类型与语法

- 新文件首行 `declare(strict_types=1);`，避免隐式类型转换。
- 参数、返回值、属性写类型；联合类型按实际取值范围收窄。
- 优先使用 `readonly`、枚举、构造器属性提升等 PHP 8.x 特性，但以项目最低版本为准。
- 避免动态属性；确需扩展时显式声明或使用数组结构。

反例：在 PHP 8.2+ 项目使用动态属性，升级时触发弃用告警。

## PSR 与自动加载

- 命名空间与目录一一对应（PSR-4），类名与文件名一致。
- 代码风格遵循 PSR-12；格式化交给项目既有工具，不手工对齐。
- 一个文件只放一个类（或一组紧密相关的声明），避免副作用。

## Composer

- 提交 `composer.lock`，部署使用 `composer install --no-dev`。
- 升级依赖先读变更日志，按小版本逐步升级；破坏性变更单独提交。
- 不在生产环境执行 `composer update`。
- 需要修改第三方代码时使用 patches 或 fork，记录来源、原因与移除条件。

## 版本兼容

- 以 `composer.json` 的 `require.php` 为准；CI 覆盖最低版本与当前稳定版本。
- 新语法先确认最低版本支持；不支持时用等价写法。
- 弃用告警视为待修问题，不长期忽略。

## 错误处理

- 异常携带上下文（业务标识、参数摘要），不打印敏感字段。
- 不吞异常、不用 `@` 抑制；捕获后要么处理、要么带上原因重新抛出。
- 对外错误码稳定；内部日志保留堆栈与请求 ID。

## 框架约定

- Laravel：沿用 Eloquent、FormRequest、Policy、队列与迁移约定；业务逻辑不写进控制器。
- ThinkPHP：沿用其验证器、中间件与模型约定；不混用另一框架的模式。
- 框架升级按官方升级指南逐项处理，不跳版本。
